# Businesses E2E: GitHub Actions Secrets setup

The Businesses workflow uses ten repository-level GitHub Actions secrets. Each
parallel matrix job receives only its selected resource slot and runs one
Playwright worker. No credential or business-data pool file is stored in the
repository or generated by the workflow.

Create these repository Actions secrets:

```text
BUSINESSES_SLOT_00
BUSINESSES_SLOT_01
BUSINESSES_SLOT_02
BUSINESSES_SLOT_03
BUSINESSES_SLOT_04
BUSINESSES_SLOT_05
BUSINESSES_SLOT_06
BUSINESSES_SLOT_07
BUSINESSES_SLOT_08
BUSINESSES_SLOT_09
```

GitHub secret names cannot contain hyphens, so the secret name uses an
underscore while the `SLOT_ID` inside it remains `slot-00` through `slot-09`.
The current workflow has ten active matrix slots. Provisioning-matrix rows 11
and 12 are reserves; they do not run unless the implementation is expanded with
corresponding credentials, repository secrets, supported slot IDs/tags, and
matrix jobs.

Before provisioning, rotate every account password and replace every seeded
business name that was previously committed. Removing plaintext from this
branch does not remove it from Git history, existing clones, old logs, caches,
or prior test artifacts.

## Secret value schema

Each `BUSINESSES_SLOT_NN` value must be one flat JSON object with exactly the
same keys. The following is a placeholder for `BUSINESSES_SLOT_00`:

```json
{
  "VERSION": 1,
  "SLOT_ID": "slot-00",
  "TAXPAYER_USERNAME": "placeholder-taxpayer-00@example.invalid",
  "TAXPAYER_PASSWORD": "replace-with-rotated-password",
  "MUNICIPAL_USERNAME": "placeholder-municipal-00@example.invalid",
  "MUNICIPAL_PASSWORD": "replace-with-rotated-password",
  "AGS_USERNAME": "placeholder-ags-00@example.invalid",
  "AGS_PASSWORD": "replace-with-rotated-password",
  "MUNICIPALITY": "PLACEHOLDER TEST MUNICIPALITY 00",
  "RESET_MUNICIPALITY": "PLACEHOLDER ISOLATED RESET MUNICIPALITY 00",
  "DEFAULT_BUSINESS": "PLACEHOLDER DEFAULT BUSINESS 00",
  "FUNDED_BUSINESS": "PLACEHOLDER FUNDED BUSINESS 00",
  "DRAFT_BUSINESS": "PLACEHOLDER DRAFT BUSINESS 00",
  "ZERO_PAYMENT_BUSINESS": "PLACEHOLDER ZERO PAYMENT BUSINESS 00",
  "ACTIVE_BUSINESS": "PLACEHOLDER ACTIVE BUSINESS 00",
  "INACTIVE_BUSINESS": "PLACEHOLDER INACTIVE BUSINESS 00",
  "REQUIRED_FORMS_BUSINESS": "PLACEHOLDER REQUIRED FORMS BUSINESS 00",
  "DELINQUENCY_BUSINESS": "PLACEHOLDER DELINQUENCY BUSINESS 00",
  "FILINGS_BUSINESS": "PLACEHOLDER BUSINESS WITH FILINGS 00"
}
```

`VERSION` must be the number `1`. `SLOT_ID` must match the matrix slot. Every
other field must be a non-empty string. Extra keys are rejected.

The business-state contract is:

Every configured `*_BUSINESS` value below is the record's exact displayed DBA,
because the suite uses it as the grid-row anchor. `ACTIVE_BUSINESS` additionally
requires Business Name and DBA to be identical, as described after this list.

- `MUNICIPALITY`: the normal test municipality visible to that slot's
  municipal and AGS accounts. It must contain disposable E2E data, never
  production data.
- `RESET_MUNICIPALITY`: a sacrificial municipality used only by TC32. It must
  be different from `MUNICIPALITY` and must not contain shared test data.
- `DEFAULT_BUSINESS`: a compatibility DBA for default-business flows.
- `FUNDED_BUSINESS`: a compatibility DBA for funded-business flows.
- `DRAFT_BUSINESS`: a compatibility DBA for draft-business flows.
- `ZERO_PAYMENT_BUSINESS`: a compatibility DBA for zero-payment flows.
- `ACTIVE_BUSINESS`: an active seeded business usable for details, dates,
  notes, documents, forms, and taxpayer views.
- `INACTIVE_BUSINESS`: a seeded closed or inactive business used by close-date
  and status-restriction tests.
- `REQUIRED_FORMS_BUSINESS`: a seeded business on which the monthly required
  form can safely be added and removed. In slot 08 it must have no enabled
  required forms so TC20 can verify the `None` filter against that exact DBA.
- `DELINQUENCY_BUSINESS`: a seeded business whose delinquency tracking date can
  be updated. It must be visible under the AGS grid's default Operating Status
  filter.
- `FILINGS_BUSINESS`: a seeded business with filings, so deletion is expected
  to be rejected. It must be visible under the AGS grid's default Operating
  Status filter.

The four compatibility fields are aliases, not four additional uniqueness
boundaries. `DEFAULT_BUSINESS`, `FUNDED_BUSINESS`, and `DRAFT_BUSINESS` may use
the same DBA. `ZERO_PAYMENT_BUSINESS` may also overlap another compatibility or
state-specific business category. More generally, each of these four fields may
equal any other configured business field. Within one slot, only the original
five state-specific fields (`ACTIVE_BUSINESS`, `INACTIVE_BUSINESS`,
`REQUIRED_FORMS_BUSINESS`, `DELINQUENCY_BUSINESS`, and `FILINGS_BUSINESS`) must
remain distinct from one another.

Every `ACTIVE_BUSINESS` used by the current suite must also have its Business
Name and DBA equal to the configured value, the location address `123 Desert
Road`, address line 2 `Suite 100`, city `Dune`, state `AK`, ZIP code `90210`,
and the required form `Food and Beverage Tax Return (Monthly)`. TC39 and TC38
assert those seeded attributes directly. It must also have a non-empty FEIN/SSN
that the taxpayer and municipal reveal controls can unmask; TC27, TC19, and
TC40 assert that behavior. Treat these requirements as part of the slot
contract when cloning or rotating the active record.

At each slot index, the taxpayer must own or see the appropriate seeded
businesses, the municipal account must manage them, and the AGS account must
reach `MUNICIPALITY`. Across all ten active slots, use globally unique usernames,
normal municipalities, and reset municipalities. Every `RESET_MUNICIPALITY`
must also be outside the complete set of normal `MUNICIPALITY` values. This
prevents account and municipality-wide state from being shared by parallel jobs,
and is especially critical for slot 00 because TC32 deletes everything in that
reset target after the matrix finishes.

Do not impose blanket cross-slot uniqueness on all business fields. Follow the
approved provisioning map for business reuse; in particular,
`FILINGS_BUSINESS` may intentionally be shared across slots. Avoid sharing a
mutation-sensitive record when parallel tests could change the same state. Do
not reuse a separate Filings-project account, municipality, or business unless
both workflows are put behind one shared concurrency lock.

Runnable matrix tests and TC32 that create a new business do not require
another secret field. They derive a non-secret name suffix, FEIN, and state-tax
ID from the slot, test, workflow run, and worker process so parallel jobs do
not create the same data.
Successful generated-business flows remove their temporary records. A failed
attempt can still leave its uniquely named record, and document-upload tests
intentionally add documents to seeded active businesses, so periodically prune
or reseed these test-only municipalities.

## Create the repository Actions secrets without a local data file

For each slot:

1. Open **Settings > Secrets and variables > Actions** in the repository.
2. Select **New repository secret**.
3. Enter `BUSINESSES_SLOT_00` (then the corresponding name for later slots).
4. Build and validate the JSON in an approved ephemeral secret-entry session.
5. Minify it and paste it directly into GitHub's secret value field.
6. Submit it, clear the clipboard, and close the session without saving it.
7. Repeat through `BUSINESSES_SLOT_09`.

Do not create a `.env`, JSON pool, PowerShell script, shell-history entry,
artifact, or repository file containing these values. GitHub does not expose a
stored secret's plaintext afterward, so a credentialed local run cannot fetch
the slots. Run it in GitHub Actions or provide one slot through an explicitly
approved process environment.

Cross-slot username and municipality uniqueness, plus the intentional business
alias map, must be checked during provisioning and rotation while all proposed
values are available in the same approved in-memory session. A matrix job
intentionally receives only one secret, so its runtime validator cannot compare
that secret with the other nine.

## Validation and masking

The selected-slot parser rejects invalid JSON, missing or unknown fields,
blank values, an incorrect version or slot ID, duplicate role usernames,
duplicates among the five state-specific business fields, an unsafe reset
municipality, and values over GitHub's 48 KiB secret limit. Intentional aliases
through the four compatibility fields are accepted. Errors never echo configured
values.

Because GitHub does not guarantee masking of fields extracted from structured
JSON, the validator registers the complete raw JSON and all seventeen sensitive
string fields with the runner's masking command before browser installation:
six username/password fields, two municipality fields, and nine business
fields. `VERSION` and `SLOT_ID` are intentionally not registered as separate
masks because they are non-secret identifiers. The automatic worker fixture
parses the slot before a browser is launched and immediately deletes the
serialized JSON from the worker environment. Do not print the parsed slot,
credential fields, business values, or the process environment.

## Workflow order and parallel allocation

The workflow has three ordered stages:

1. A non-secret preflight explicitly fails a manually dispatched ref other than
   `main`, then runs `npm ci`, type-checking, resource parser/guard tests, and the
   slot/account/business allocation validator once. No slot secret is available
   to this job.
2. After preflight succeeds, the ten matrix jobs run in parallel. Each job
   receives only its selected repository secret, validates and masks that value,
   installs the browser, and runs its tagged tests with one worker.
3. After every matrix job succeeds, the isolated TC32 lane uses slot 00 and runs
   by itself to reset its sacrificial municipality.

[`nlg-business-e2e.yml`](../.github/workflows/nlg-business-e2e.yml) defines a
static ten-entry matrix:

```text
slot-00 / BUSINESSES_SLOT_00 / @slot-00
slot-01 / BUSINESSES_SLOT_01 / @slot-01
...
slot-09 / BUSINESSES_SLOT_09 / @slot-09
```

Each matrix entry runs `--workers=1`; parallelism comes from the ten jobs. Tests
inside one job consistently use that slot's taxpayer, municipal, AGS,
municipality, and seeded businesses. The explicit allocation is:

```text
@slot-00: AGS TC1; Municipal TC6, TC13; Taxpayer TC27
@slot-01: AGS TC2; Municipal TC19, TC14; Taxpayer TC36
@slot-02: AGS TC3; Municipal TC40, TC15; Taxpayer TC38
@slot-03: AGS TC52, TC53; Municipal TC7, TC21; Taxpayer TC39
@slot-04: AGS TC9, TC33; Municipal TC44, TC16; Taxpayer TC43
@slot-05: AGS TC55, TC51; Municipal TC54, TC23, TC17
@slot-06: AGS TC4, TC10; Municipal TC57, TC18
@slot-07: AGS TC47, TC45; Municipal TC59, TC48
@slot-08: AGS TC60, TC49; Municipal TC46, TC20
@slot-09: AGS TC61, TC42; Municipal TC5, TC41
```

This gives four or five tests per slot. AGS usage is one or two tests per slot,
municipal usage is two or three, and the five taxpayer tests occupy five
different slots. These are the closest possible distributions for 17 AGS, 21
municipal, and five taxpayer matrix tests.

Business tags identify use of the active, inactive, required-forms,
delinquency, filings, and generated records. Tests that adopt a compatibility
alias use `@business-default`, `@business-funded`, `@business-draft`, or
`@business-zero-payment`; unused compatibility categories do not require a slot
allocation. For categories used by runnable tests, the allocation validator
requires the maximum and minimum per-slot counts to differ by at most one.
Runtime guards also reject a credential or seeded-business access when the test
does not carry its matching role/category tag, including indirect helper use.
Skipped tests stay untagged; removing a skip forces the test to be allocated
before CI accepts it.

TC32 resets all data in `RESET_MUNICIPALITY`. It is excluded from the matrix
and runs only after all ten jobs succeed, using `BUSINESSES_SLOT_00`, one worker,
and `E2E_RUN_GLOBAL_STATE=true`. The Playwright configuration selects only TC32
in that mode. Never point `RESET_MUNICIPALITY` at the normal test municipality.

The workflow concurrency group is `businesses-e2e-dev`, with cancellation
disabled, so two Businesses workflow runs cannot overlap. It has only manual
and scheduled triggers. The non-secret preflight fails a manual run selected
from anything other than `main` before the secret-consuming jobs can start. Do
not add pull-request or repository-dispatch triggers. Checkout credentials are
not persisted, actions are pinned to immutable commits, browser artifacts are
disabled by default, and no test-result artifact is uploaded.

The preflight ref check provides an early, friendly failure; it is not a secret
security boundary because branch code can modify or remove it. Repository
Actions secrets are not bound to `main`: workflow code that explicitly
references them can receive them. Treat collaborators who can modify and run
workflow code as inside the secret trust boundary, strictly limit repository
write and Actions permissions, and restrict branch-ruleset bypass access.

Branch gating in the workflow is not a substitute for review controls. Any
workflow, test, helper, configuration, or dependency change executed by a
credentialed job could read its selected slot. Add the actual responsible team
or user to `CODEOWNERS` for `.github/workflows/nlg-business-e2e.yml` and the
complete executable `businesses` tree, then use a branch ruleset on `main` that
requires code-owner review. This guide intentionally does not invent an owner.

The Playwright configuration uses only its console reporter because external
reporters can transmit unredacted failure details outside GitHub's log-masking
boundary. The dormant Teams sender posts raw failure text, and GitHub runner
masks do not redact outbound HTTP bodies. If Teams reporting is re-enabled,
remove error bodies or redact every selected-slot value before sending them.

The legacy `checkly.config.ts` command is not a supported credentialed runner:
Checkly cannot read the repository Actions secrets, and a single injected slot
must not execute tests assigned to the other nine slots. Keep credentialed
execution in this GitHub Actions workflow unless another runner gets an
equivalent selected-secret provider and one-slot grep. If an approved process
has ever deployed the daily Checkly check, disable or undeploy that check in
Checkly itself; editing this repository does not stop an already deployed
schedule. If an approved process has already injected one slot into the process
environment, its matching local command is:

```text
npm run test:playwright -- --grep="@slot-00" --workers=1
```

Change the tag and expected slot ID together. Do not run the unfiltered suite
with a single selected secret; the fixture rejects a slot/tag mismatch before
browser work.

## Rotation and adjacent secrets

For every provisioning or rotation session:

- Validate all ten exact schemas and slot IDs before upload.
- Reject duplicate usernames, normal municipalities, or reset municipalities
  across active slots.
- Reject every reset municipality that matches any slot's normal municipality.
- Keep the original five business fields distinct within each slot, while
  preserving the approved compatibility aliases and any approved cross-slot
  `FILINGS_BUSINESS` sharing.
- Verify same-slot access from taxpayer, municipal, and AGS accounts.
- Update each complete slot atomically as one repository Actions secret.
- Run the workflow manually and confirm parser/allocation preflights.
- Clear clipboard and process memory where practical.
- Restrict repository-secret administration and repository write access.

The formerly committed Teams webhook and Cypress recording key are separate
service credentials, not slot data. Rotate them too. Store the replacement
values as `BUSINESSES_TEAMS_WEBHOOK_URL` and `CYPRESS_RECORD_KEY` only where the
corresponding optional integration runs; do not add either value to a slot.
